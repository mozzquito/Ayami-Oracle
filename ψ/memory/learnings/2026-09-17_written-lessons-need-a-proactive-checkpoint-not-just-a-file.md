# A written lesson needs a firing checkpoint, not just a file

On 2026-09-15 a retro explicitly flagged: this Oracle should proactively bring in zcode/agy at
each SDLC stage of substantive work, per the parent CLAUDE.md, rather than waiting to be asked.
The very next working session (2026-09-16/17, same project) then proceeded through several
substantive stages — updating a real SOW artifact, researching real procurement paths for a bank
RFP — and zcode/agy were consulted only when the user typed the literal tag `/zcode /agy`
themselves. Never once initiated proactively, despite the lesson being freshly written one day
earlier and presumably loaded into context via the memory system.

**Why**: A lesson file is passive. It states a rule but does not itself create a trigger point in
the flow of work where that rule gets checked. Without an explicit "have I done X yet at this
stage" checkpoint, the default behavior (react to what's asked, don't volunteer process overhead)
wins by default, and the lesson sits unread-in-practice even though it was technically "in
memory."

**How to apply**: When a retro identifies a proactive-behavior gap (should have asked, should have
consulted, should have verified before proceeding), don't just record the insight — attach it to a
concrete trigger: name the exact stage/action where the check should fire ("before publishing any
artifact update," "before answering a question that will drive real spending decisions"). At the
start of a new session or new stage of substantive work, explicitly scan open lessons for
triggers matching the current stage, rather than assuming a general "I read my memories" pass
was enough. See [[project_uob_bank_sccm_exchange]] for the live case this recurred in.
