# Extending an existing mechanism is an implicit claim it currently works — verify that claim

## What happened

Asked to add the same ✅/❌ Discord quick-confirm flow that `market-backtester`'s own trade
signals already have, to a second, independent paper-trading experiment (Grok Bot's). The
natural approach was purely additive: read `discord-bot/bot.mjs` (the persistent process
that listens for Discord reactions), understand its regex/logging pattern, and extend it
with a second set of markers for the new project.

Before writing any new code, restarting the running `bot.mjs` process to confirm it was
healthy revealed it had been crash-looping on every launchd start — `node_modules` was
missing entirely (`Cannot find package 'dotenv'`). This meant `market-backtester`'s own
✅/❌ confirm-flow — the exact mechanism being extended — had been non-functional for some
unknown period, discovered purely as a side effect of building a similar feature for a
different project, not because anyone had reported the original one as broken.

The reason this went unnoticed: unlike an hourly cron job (which fails loudly and often,
and already had heartbeat/error-alert coverage in this project), a Discord reaction-confirm
flow only fires when (a) a real trade signal happens, and (b) a human then clicks a
reaction — both infrequent events. A silent failure in the listener process has no natural
trigger to surface it quickly.

## Generalizable rule

When a task is "add the same X that already exists over there" to a new location, treat
verifying that the *existing* X currently works as part of the task, not an assumption to
carry over from "it was clearly built correctly." This matters most for:

- Low-frequency, human-in-the-loop mechanisms (a rarely-clicked button, an occasional
  webhook, an admin-only trigger) — these fail silently because nothing routinely exercises
  them.
- Background/daemon processes managed by something outside the immediate task (launchd,
  systemd, a supervisor) — a missing dependency or crash can leave them permanently down
  with no automatic restart-and-alert.

A quick concrete check (restart the process, hit the endpoint, trigger the webhook once)
before extending it costs little and can catch a real, otherwise-invisible production gap
— exactly the kind of thing that would otherwise only surface when someone actually needed
the feature and it silently didn't work.

## Related: cross-language marker verification

A second, narrower lesson from the same session: when a machine-readable marker embedded
in a message will be generated by one language/process and parsed by a regex in a
*different* one (here: Python generating a Discord message, JavaScript parsing it), verify
the exact generated string against the actual parsing regex directly — run both sides
together with a real example, don't just eyeball that the two definitions "look
compatible." A formatting assumption that's fine in isolation (e.g. a float always
rendering as plain decimal) can silently break the parsing side without either language's
own tests catching it, since each side's tests only exercise its own code.
