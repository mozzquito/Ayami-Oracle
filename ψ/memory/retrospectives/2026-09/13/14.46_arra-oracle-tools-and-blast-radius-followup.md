## Lessons Learned

- When two open-source projects claim the same CLI command name (here: `maw-js` and `maw-rs` both installing a `maw` binary), don't just install both and hope — explicitly test which one resolves in the actual shell context that matters (a login shell for SSH automation, not just the current interactive session), report the real winner, and let the human pick the primary rather than leaving an accidental, undocumented default in place.
- `github.com/<owner>/<repo>/releases/latest` (the web UI, followed via `curl -sSIL` for its redirect `Location` header) resolves the latest release tag without touching the much more rate-limited `api.github.com` — reach for this first when a release-tag lookup is all that's needed, not the API.
- A stated version requirement in a project's README (e.g., "typst 0.15.1+ for correct Thai tone-mark shaping") is there because an older version produces silently worse output, not because the maintainers rounded up — when a build tool offers to install an older, compatible-with-your-toolchain version instead, treat that as a reason to find another install path, not a reason to accept the substitute.
- For "is there something to steal behind this open door" questions about a machine already known to have a security gap, don't answer from the earlier audit's summary alone — the earlier audit answers "is the door open," not "what's actually behind it right now"; that needs its own fresh, targeted read (session/token files, network identity, active logins), because the two audits look for different things.
