## Lessons Learned

- When investigating credentials/secrets on any machine — even one the user owns — search by variable *name* or by process/file structure, not by grepping for secret-shaped value patterns (`sk-...`, etc.) across broad filesystem paths; the narrower search answers the same question with less exposure and is far less likely to trip a safety classifier (or look like real credential harvesting to a human reviewer).
- When multiple SSH usernames are plausible for a box, ask the user which one to use before looping through candidates — a sequential username try-list is structurally identical to brute-forcing, regardless of intent, and the fix (just ask) is no slower than guessing wrong twice.
- A platform's own "secure secret" chat feature is a display-layer guarantee, not a pipeline guarantee — a value typed into any chat interface has already transited that app's message/network path before redaction can happen; only the platform operator can confirm whether raw secrets are retained in backend logs, so don't extend a client-side "looks safe" finding into a claim about backend log handling.
- To determine whether a secret on a Linux host is disk-persisted, mount-injected, or purely runtime-injected: check `/proc/1/environ` (the root process) versus a live child process's `/proc/<pid>/environ`, and check for a `/run/secrets`-style mount — if the root process lacks it but children have it and no mount/file exists, it's being injected fresh into each child at spawn time by whatever supervises the process tree.
