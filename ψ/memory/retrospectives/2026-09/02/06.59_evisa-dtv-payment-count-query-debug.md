## Lessons Learned

- **When checking a column's viability for a filter, verify both its type AND its population rate in the same diagnostic pass** — `COUNT(*) vs COUNT(col)` (or a `MIN`/`MAX`/non-null count, as used later in this same session) costs nothing extra to add to a type-check query, and catches "technically the right type, but always NULL" before it produces a misleading 0-row result.
- **A table/column name surfaced once in an unrelated diagnostic scan is worth remembering and re-offering later** — `VDC_APP_APPLICATION_PAYMENT` was found via a generic `%STATUS%` column search days earlier for a completely different status-lookup problem, not a payment investigation, and turned out to be exactly the right table when a payment-date question came up later. Broad diagnostic scans have value beyond their immediate question.
- **When two verified options exist for the same query and they trade off differently (performance vs. correctness edge cases), present both honestly and let the user decide** rather than silently picking one — the user may have context (how the report will be used, how often it runs) that changes which tradeoff matters more.
