## Lessons Learned

1. **Windows PowerShell 5.1's `Invoke-RestMethod`/`Invoke-WebRequest` resolve their proxy via
   WinINET (per-user `HKCU\...\Internet Settings`), not WinHTTP.** `netsh winhttp set proxy` (a
   machine-wide setting) has no effect on these cmdlets. When one succeeds interactively but fails
   from a Windows Service context with a DNS-resolution-shaped error, pass the proxy explicitly on
   the call itself (`-Proxy "http://host:port"`) rather than trying to fix it at the OS-config
   layer.
2. **A Windows service's effective network path (DNS, proxy, VPN) can differ completely from the
   interactively logged-in user's session, even under the identical account.** Testing
   connectivity via an interactive RDP/console session does not prove a service (GitLab Runner or
   any other) can reach the same destination — verify from inside an actual job/service execution
   before trusting an interactive test as a stand-in.
3. **GitLab's "Access Tokens" page exists in two different scopes that produce fundamentally
   different credentials**: User Settings → Personal Access Token (acts as that user, whatever
   role they hold instance-wide); Project Settings → Access Tokens → Project Access Token (spawns
   a new bot user scoped to just that project, with a role picked at creation time). Always
   confirm which kind was created and check its actual `access_level` via the API
   (`GET /api/v4/projects/:id/members/all`) before assuming write permissions — a 403 on a
   write-scope call is a strong signal the token is a lower-role project bot, not a scope
   problem.
4. **When an automation classifier blocks a sudo-over-SSH command to a remote host, it blocks the
   entire class of action, including read-only variants** (a plain `cat` on a password file was
   blocked the same as a disk-partition-modifying command). Don't retry variations hoping one
   slips through — hand the exact command to the human to run themselves immediately.
5. **A CI job that cycles a stateful resource (an IIS app pool, a service, a lock) must check
   current state before acting, not assume the previous run left it in the expected state.** A
   job that dies mid-cycle (as one did here, between `Stop-WebAppPool` and `Start-WebAppPool`)
   leaves that resource in whatever state it died in, and the next unconditional run will throw
   on an assumption that no longer holds.
