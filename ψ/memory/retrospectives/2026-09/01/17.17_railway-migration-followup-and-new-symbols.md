## AI Diary

clean example of a mistake compounding on itself. On 2026-08-28 I found a real problem — a
service ID that didn't match anything — investigated it, found what looked like the right answer
via `railway status --json`, wrote a careful commit message explaining the fix, and moved on
confident it was resolved. It wasn't. I had pulled a ServiceInstance ID (environment-scoped) when
the GraphQL call actually wanted a top-level Service ID (project-scoped) — two different values

I never had a way to fully verify it at the time (the GraphQL auth issue meant I couldn't test the
corrected value either) — I trusted structural pattern-matching (which service instance carries
the live cronSchedule) over direct confirmation, because direct confirmation wasn't available.

handing me a build-log URL today that happened to contain the *other* ID, which made the
discrepancy impossible to miss. That's a bit humbling: I got the right answer this time because
the tool surfaced contradictory evidence unprompted, not because I went looking for it. I did
follow through properly once I saw it — didn't just paper over the URL as a fluke, actually
reasoned out *why* two different IDs could both look locally correct (the Service/ServiceInstance
distinction), and documented that reasoning in the script itself so a future me (or Boss) has the
actual explanation, not just a changed number.

## Lessons Learned

- When a platform's data model distinguishes between similarly-named identifiers for "the same"
  logical resource (a project-scoped ID vs. an environment-scoped instance ID, a display name vs.
  an internal key), don't trust a single indirect signal (a field matching by content, like
  cronSchedule) as proof you've found the right one — cross-check against a second, structurally
  different source (here: the ID embedded in a tool-generated URL) before treating the correction
  as settled, especially when the "obviously correct" verification path (the API call itself) is
  known to be unavailable.
- When a user reports several distinct problems in one message, triage explicitly before acting —
  identify which one has the most severe/time-sensitive consequence (here: total notification
  silence, which echoes a past real incident) and address that first, rather than working through
  the list in the order it was written or trying to solve all three simultaneously.
- For "what's worth doing" questions in a domain with real financial/decision stakes (which coin,
  which investment), ground every answer in verifiable computed data (real backtests, real
  historical prices) rather than pattern-matching from general knowledge or trend-following
  intuition — this keeps the answer auditable and keeps the actual recommendation-making
  authority with the human reviewing real numbers, not with the assistant's opinion.
