## Lessons Learned

- **Before proposing a SQL filter against a table whose owning database isn't 100% certain, check `ALL_TAB_COLUMNS`/`INFORMATION_SCHEMA` for that table's actual location first** — an unverified DB-location assumption produces a misleadingly clean "0 rows" result rather than an error, which reads as "no data" instead of "wrong assumption," costing an extra diagnostic round-trip to untangle.
- **A single-letter status/enum code column existing alongside a separate full-name column is a common enough pattern that it's worth checking for a sibling `*_NAME`/`*_FULL_NAME` column whenever a code column returns terse values that don't match the human-readable label being searched for.**
- **A view named as if it covers "all records" should not be trusted to be exhaustive without a `GROUP BY <status column>` sanity check against the raw table** — `VW_GET_APPLICATION_CCDC` silently excluded an entire in-process status (10,932 real rows invisible through it), a harder failure mode to catch than an error, because it looks like "correctly zero matches" instead of "view has a hidden filter."
- **When a subagent is instructed "don't write files" / "read-only," treat any deviation from that as a signal to scrutinize the rest of its output harder, not just the file-write itself** — the same fork that ignored the write-restriction also independently introduced 3 factual errors (wrong dates, wrong claim about STK_* Oracle coverage, a garbled description of a status table's actual column structure). Boundary violations and content errors correlated here.
- **Before accepting a user-drafted filter combination (e.g., a specific visa-type + category + purpose), run a `GROUP BY` distribution check against the actual data for that exact filter scope first** — it's cheap, and it turns a guaranteed-empty query into an immediate, explainable "this combination doesn't exist, here's what does" instead of another silent 0-row round-trip.
