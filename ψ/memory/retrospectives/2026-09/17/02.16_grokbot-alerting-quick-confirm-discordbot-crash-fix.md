## Honest Feedback

1. **The `bot.mjs` crash was a real, silent production gap that had nothing to do with
   tonight's work** — `node_modules` was entirely missing, meaning market-backtester's own
   ✅/❌ confirm-flow had been non-functional for an unknown period before I happened to look
   at this file for an unrelated reason. This is worth naming plainly: a feature that only
   fires occasionally (a real trade signal, then a real human clicking a reaction) can stay
   silently broken for a long time with nothing surfacing the failure, unlike the cron jobs
   this session already has heartbeat/error-alert coverage for. There's no equivalent
   "is bot.mjs actually running and connected" check anywhere in this project.
2. **The Discord reaction-count check was the right verification tool, but timing made the
   first read misleading** — Discord's own message/reaction API is closer to ground truth
   than my bot's own logs (which print nothing on a successful reaction, only on error), but
   a several-second propagation gap meant the very first check came back looking like a
   real failure when it was actually just too early. Worth building in a short wait before
   the first check next time this pattern comes up, rather than treating the first negative
   result as final.
3. **Two independent, unrelated fixes came out of following one small feature request all
   the way through** (the missing-node_modules crash, and the scientific-notation marker
   risk caught before it ever shipped) — both were only found because the task was treated
   as "understand and verify the existing mechanism," not "write new code that plausibly
   fits the pattern." Neither would have surfaced from reading bot.mjs's source alone
   without actually trying to run it.

## Lessons Learned

- When asked to replicate or extend an existing feature/mechanism in another part of a
  system, verify that the *existing* mechanism is actually currently working before
  building on top of it — don't assume it still works just because it's clearly designed
  to and presumably worked when it was built. A silently-broken dependency (a crashed
  background process, a missing package) can sit unnoticed indefinitely for a
  low-frequency, human-in-the-loop feature (a confirm button someone clicks rarely) in a
  way that would be caught immediately for something checked every hour.
- When a machine-readable marker embedded in a human-facing message will be parsed by a
  regex in a *different* language/process than the one generating it (here: Python
  generating, JavaScript parsing), verify the exact generated string against the actual
  parsing regex directly — don't just eyeball that the two definitions "look compatible."
  A cross-language string-format assumption (e.g., that a price will always render as
  plain decimal) is exactly the kind of thing that looks obviously fine in isolation and
  silently breaks in combination.
- When verifying a live user-driven action worked (a button click, a form submission) by
  checking external state afterward, allow for propagation delay before treating a
  negative first check as conclusive — but still report an unexpected negative result
  honestly rather than assume success, and re-check rather than silently retry-and-hide
  the first failed check.
