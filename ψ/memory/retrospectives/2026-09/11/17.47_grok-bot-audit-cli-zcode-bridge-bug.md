This forced a much slower verification path (direct SSH + SQLite queries) than the tool was supposed to provide, and I only trusted the tool's "no reply yet" at face value for a couple of checks before escalating to ground-truth verification.

## Lessons Learned

- When a relay/bridge tool exposes a status field for an async operation, treat a "still pending" status as *unverified*, not as *false* — but also don't let it sit unquestioned for long: if a human-visible channel (screenshot, UI) contradicts the tool's reported state, go straight to the underlying data store rather than continuing to poll the tool that already proved unreliable.
- Before downloading third-party vendor software onto a remote box, cross-check the download domain against a domain already verified earlier in the same session (here: `zcode.z.ai`, matching the already-used `api.z.ai`) — a search engine's top result can surface a plausible-looking but unverified lookalike domain (`zcode-z.com`) alongside the real one.
- Electron-packaged desktop CLIs frequently support `ELECTRON_RUN_AS_NODE=1 <binary> <bundled-script.js>` to run the bundled Node runtime headlessly, without a display or FUSE — worth testing before assuming a GUI-distributed tool is unusable in a headless/SSH context.
- A three-noun ambiguous request ("X /Y /Z") deserves a clarifying question before the most mechanically-obvious reading (e.g., "these are invocable skills, so invoke them") gets acted on — mechanical availability of an interpretation isn't evidence it's the right one.
