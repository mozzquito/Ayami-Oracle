## Lessons Learned

- **Before telling a user "tool X fixes problem Y," trace the actual mechanism, not just the description.** A tool's stated purpose can overlap with a stated pain point at the surface level while operating at a completely different layer of the stack (a Claude-Code-level Bash hook vs. a subprocess's internal file writes; a CLI's own call-logging vs. a *different* CLI's API calls). This generalizes past this session: any fit-claim between a tool and a named problem needs one extra "where exactly does this intercept" check before it's said out loud, not after the user asks for install details.
- **When running a QC loop over LLM-generated research, watch specifically for confident-sounding statistics** (star counts, percentage figures, benchmark numbers) — they're the highest-value thing to challenge, because a wrong name is obviously wrong but a wrong number reads as credible. Instructing the re-dispatch to explicitly forbid unverified numbers ("ห้ามอ้างตัวเลขที่ไม่มั่นใจ") fixed it on the first retry.
- **A dynamic `/loop` with a hard deadline and a per-round exclusion list is a solid pattern for iterative research that must not repeat itself** — carrying the cumulative "already covered" list forward into every dispatch prompt, plus a same-round re-dispatch on QC failure before advancing, kept 6 rounds of parallel two-source research free of duplicates without needing a human to track it.
