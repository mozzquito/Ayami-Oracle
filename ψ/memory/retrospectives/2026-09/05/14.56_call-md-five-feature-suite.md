   silently (exit code 139, no readable error) before I remembered - and then had to
   re-derive - that this project's native modules are rebuilt specifically for Electron's
   Node ABI and must be exercised via `ELECTRON_RUN_AS_NODE=1 <Electron binary>` instead.

## Lessons Learned

Generalizable rules, not session-specific complaints:

1. **When a second-opinion LLM CLI (zcode/agy or similar) makes a specific, checkable claim
   about a third-party API/SDK's exact shape (field names, method signatures, nullability),
   verify it against the actual installed source/types before applying a fix** - this class
   of claim is disproportionately likely to be confidently wrong, even from otherwise
   reliable reviews in the same session.

2. **Before launching any long-running dev/server process for live testing, check for an
   already-running instance first** (`ps aux | grep`), especially when the user's own
   session might already have that exact app open - true even (especially) when you were
   just driving that same window via computer-use moments earlier.

3. **For Electron apps with native Node modules (better-sqlite3, etc.), any ad-hoc sanity
   check must run via the app's own Electron binary with `ELECTRON_RUN_AS_NODE=1`, never
   plain system `node`** - the native binary is ABI-compiled specifically for Electron's
   bundled Node version and segfaults silently under a mismatched runtime.

4. **When designing search, chunking, or tokenization over content that may include
   non-space-delimited scripts (Thai, and generally CJK/Southeast Asian scripts), test the
   specific mechanism against real non-Latin-script sample content before trusting the
   design** - word-based tokenizers/splitters silently degrade to treating an entire
   paragraph as one token, and this bit both the transcript-chunking design and the FTS5
   tokenizer choice in this session before being caught.
