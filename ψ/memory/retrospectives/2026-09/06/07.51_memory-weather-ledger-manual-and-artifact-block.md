The fix this time was mechanical (rebuild, save it into `ψ/incubate/` instead), but the more useful realization is that "where does this end up living" is a question I should ask *before* attempting the risky step (the publish attempt), not discover as a gap after it fails. ## Honest Feedback

**Friction 1 — a request had two independent asks (cron time + report content) and only one got fully carried through.** The user's "ทำ cron อัพเดท ทุกวันศุกร์เวลา 12.00 น" was two separate, checkable facts (the automation exists; the automation fires at 12:00). I verified the first and silently let the second slide because it required touching a different file (the plist) than the one I was already editing (the script). Nothing caught this until the user's own actions two days later prompted a fresh check.

**Friction 2 — no durability check before a risky publish attempt.** Building the file directly in the session scratchpad (rather than in the permanent project location, then copying it out only if/when publish succeeded) meant the failure mode of "publish gets blocked" and the failure mode of "session ends" compounded into total data loss. A five-second habit — save the real artifact source under `ψ/incubate/` *first*, publish *from* that path — would have prevented the whole rebuild.

**Friction 3 (operational, not mine to fix) — claude-in-chrome extension connectivity was unreliable across this entire multi-day span**, failing both the local-file preview (twice, on two separate days) and a plain `lanceglass` open-in-browser request today. Every time, the actual unblock was the user opening the URL themselves. This has now happened often enough across sessions that it's worth treating "ask the user to open it themselves" as the default first move for any local URL, not a fallback after an automated attempt fails.

## Lessons Learned

- **When a user's request contains multiple independently-verifiable asks bundled in one sentence (e.g. "set up X to run at time Y"), verify each one separately before calling the request done** — don't let editing one artifact (a script) stand in as evidence the other (its schedule) was also handled.
- **Before attempting a step that might be blocked or refused (an external publish, a permission-gated action, anything with a real chance of failing) put the work's source of truth in a durable location first, and treat the risky step as something done *from* that location, not *to* a copy that only becomes durable if the step succeeds.** Session-scratchpad and other ephemeral locations are for staging, never for the only copy of finished work.
- **When the same category of external tool has now failed to connect on 3+ separate calendar days in the same environment (here: claude-in-chrome, blocked by an unrelated VPN once, disconnected outright twice more), stop treating each failure as an isolated retry-worthy incident and default straight to "ask the user to do the browser step themselves."**
