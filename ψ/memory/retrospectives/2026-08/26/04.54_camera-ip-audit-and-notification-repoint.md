## Lessons Learned

1. **When a device's own live status API (`device_state`, `device_config`, etc.) directly contradicts what a user reports observing, report the discrepancy transparently — but also ask what specifically the user was looking at when they saw the failure**, rather than treating "my API check disagrees with you" as case-closed. The user's observation may reflect a different layer (UI vs. API, a specific moment vs. current state) that a single API check won't surface.
2. **When a query-type API endpoint consistently errors regardless of payload shape, and there's a known working alternative that doesn't require reading the failing endpoint's current state first (e.g., an idempotent "set" call), it's fine to work around it for the immediate task — but say explicitly that the root cause wasn't found**, rather than letting a successful workaround imply the underlying problem was understood.
