## Architecture Decisions

- **Sizing math centralized**: `engine.compute_entry_allocation()` shared by both the backtest engine and the live `advise` command — a fix made once (the Kelly floor) automatically applies everywhere, no parallel reimplementation to drift out of sync.
- **Kelly floor over hard zero**: clipping the Kelly fraction to `max(f, KELLY_MIN_FRACTION)` instead of allowing `f=0` — a hard zero creates a permanent deadlock (no trades → no new stats → f stays 0 forever). A small probe size keeps the estimate alive.
- **Cloud notifier is pure Python (REST), not Node**: local uses `notify.mjs` (discord.js, reuses the bot's already-loaded gateway pattern) but the Railway image uses `backtester/notify.py` (raw HTTPS POST to Discord's REST API) — avoids shipping two runtimes into one container for a job that only needs to fire one message and exit.
- **State on a mounted volume, path via env var**: `BACKTESTER_STATE_DIR` override in `advisor.py` so the exact same code works against a local relative path or a Railway-mounted `/data` volume — cron containers are ephemeral by default and would silently forget every open position without this.

## Lessons Learned

- **When live-running state seems broken, check what it actually left behind before hypothesizing about why the observation tool looks wrong.** A stateful system's own persisted output (a file mtime, a DB row, a written artifact) is cheaper and more decisive evidence than reasoning about buffering/PATH/environment differences — check the artifact first, theorize second.
- **Centralize money-math logic behind one function shared by every caller, not reimplemented per entry point.** The Kelly-lockout fix and the entry-allocation logic only needed fixing once because both the backtester and the live advisor called the same `compute_entry_allocation()` — parallel reimplementations are exactly where sizing bugs silently diverge between "what was backtested" and "what actually executes."
- **A hard floor at zero on any adaptive/self-reinforcing parameter is a deadlock risk if that parameter also gates the only mechanism that could update it.** Kelly sizing hitting exactly f=0 meant no trade could ever happen again, which meant no new data could ever update the estimate — the fix (a small non-zero floor) applies to any adaptive control loop with this same "output gates its own input" shape, not just this project.
- **When a user asks "what should I bet on to maximize profit," the honest answer is structural (liquidity, minimum viable capital, what past data can rule out) — refuse to predict, and immediately follow the refusal with a concrete lower-risk alternative in the same breath**, rather than making them ask again for the actionable version.
