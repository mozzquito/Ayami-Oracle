## Architecture Decisions

- **Redis for cross-service trade history, not a shared volume**: Railway volumes are single-service. Position *state* (what the bot thinks it's holding right now) stays on the cron service's own volume — only *closed trades* mirror to Redis, since that's the only thing the dashboard actually needs to see. Smaller shared surface = smaller failure surface.
- **Real trades logged as free text, not parsed fields**: mirrors the existing diary pattern deliberately. A regex/LLM parser guessing at "เข้า 63000 ออก 65000" could silently misread a number; verbatim logging can't. Structured summarization, if ever wanted, can happen later by reading the raw file — not by trusting an inline parser with real financial numbers.
- **Two `railway.json` files, one active**: since both the cron job and the dashboard deploy from the same directory but need incompatible `deploy` blocks (`cronSchedule` vs a persistent web server), the working pattern settled on was saving both configs (`railway.cron.json`, `railway.dashboard.json`) and copying the right one over `railway.json` immediately before each `railway up --service <name>` call.
- **`trade_store.py` fails open, not closed**: every Redis operation is wrapped to swallow exceptions and return empty/no-op rather than raise — a Redis outage must never break the advisor's own local-state logic, since that's the thing actually managing real (paper) money decisions.

## Lessons Learned

- **When a delegated agent (agy, zcode, any sibling AI) gives a wrong quantitative answer once, immediately downgrade trust for the whole category of question — don't wait for a pattern to "confirm itself" over multiple incidents.** One clear falsification (contradicted by real data) is enough evidence; treating it as a fluke and re-asking a differently-framed version of the same question wastes a round-trip that could go straight to the reliable path.
- **Investigate destructive-action targets by actually checking their running state (process status, deployment source, live domain), not just their name or age.** A project named after something innocuous can be live production infrastructure; a project's creation date tells you nothing about whether it's still load-bearing.
- **When a user re-confirms a destructive action after an explicit warning, that authorizes the action itself — but a genuinely high-risk consequence (taking down a live service with real traffic, not an idle resource) deserves one more specific confirmation naming that exact consequence, not just a repeat of the original instruction.** The bar for "informed enough to proceed" should scale with the blast radius, not just the number of times the same words were said.
- **Free-text logging beats structured parsing for financial/numeric data captured casually (chat messages, quick notes) unless the parser has been rigorously tested against real inputs.** A misparsed number is worse than an unparsed one — better to defer structure to a deliberate later pass than to silently mis-record in real time.
