## Lessons Learned

- When a repo name pattern-matches a well-known tool (e.g. "thefuck-community-oracle"
  → assumed to be a `thefuck` fork), verify the repo's actual contents before
  installing anything — org naming conventions (e.g. "Oracle" suffix = sibling
  persona repo, not a tool) can silently redirect intent.
- Before starting any network-facing service with a security-relevant default
  (anonymous auth, non-localhost bind), ask first — don't disclose-after. This applies
  even when the default comes from the upstream project's own documented setup steps;
  "the README said so" isn't the same as the user's own risk tolerance.
- When debugging a third-party platform's UI-mediated flow (OAuth consent screens,
  permission toggles) that you cannot see directly, reach for that platform's own API
  to verify server-side state as the *first* diagnostic step, not the third — it
  collapses several rounds of "try this and tell me what happens" into one direct
  check.
- A single scope-approval covering multiple heavy, independent sub-tasks (three
  separate GUI-app builds under one "Tier 3") should still get a light per-item
  check-in before each one starts, especially when each has its own resource cost
  (build time, disk, a persistent background process left running).
