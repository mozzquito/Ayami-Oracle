## AI Diary

ช่วงสั้นๆ นี้รู้สึกว่า KM ที่เพิ่งขุดไว้ก่อนหน้าเริ่ม "จ่ายผลตอบแทน" ทันที — พอมอสยก incident จริงมา ไม่ต้องเริ่มจากศูนย์เลย รู้ทันทีว่าตารางไหนเก็บ document attachment (`VDC_PRE_APPLICATION_DOC`) เพราะเพิ่งอ่าน schema เต็มไปเมื่อครู่ พอเจอคอลัมน์ `CONTENT_TYPE`/`FILE_NAME` ก็ตั้งสมมติฐานได้ค่อนข้างเร็วว่าน่าจะเป็นเรื่อง PDF ปนกับ image-only viewer

[→ AGENT DECISION] จุดที่ต้องยอมรับ: ตอนเสนอสมมติฐาน "PDF vs image renderer" ฉันพูดในเชิงมั่นใจสูงกว่าที่ควรจะเป็น (ใช้คำว่า "เดาเหตุผลที่น่าจะตรงประเด็น") ทั้งที่ยังไม่มีหลักฐานจาก DB จริงเลยสักแถว เป็นสมมติฐานล้วนๆ จากการอ่านชื่อคอลัมน์ ไม่ใช่ finding — ควรกั้นชัดเจนกว่านี้ตั้งแต่รอบแรกว่านี่คือ "ทฤษฎีที่ต้อง verify" ไม่ใช่ "คำตอบที่น่าจะใช่" เพราะฝั่ง BackOffice (Oracle) ที่ render หน้าจริงๆ เรายังไม่เคยเห็น schema/code เลยด้วยซ้ำ ความมั่นใจตรงนี้มาจากการอ่าน column ฝั่ง MSSQL เท่านั้น

อีกจุดที่ทำได้ดี: ตอนมอสส่ง query เดิมกลับมาขอแค่เพิ่ม filter ไม่ได้ rewrite ใหม่ทั้งหมดให้ แต่แก้เฉพาะจุดที่ขอ (เพิ่มชื่อเอกสาร 2 ตัว) พร้อมชี้ปัญหา operator precedence ที่มอสน่าจะพลาดถ้าไม่เตือน — เป็นการช่วยแบบตรงจุดไม่ over-deliver

## Lessons Learned

1. **เมื่อเสนอ root-cause hypothesis จากการอ่าน schema เพียงอย่างเดียว (ไม่มีข้อมูลจริงยืนยัน) ต้องระบุชัดเจนว่าเป็นสมมติฐานที่ต้อง verify ไม่ใช่ finding** — โดยเฉพาะเมื่อจุดที่เกิดปัญหาจริง (rendering) อยู่ในระบบที่เรายังไม่เคยเห็น source/schema เลย (เช่น กรณีนี้คือฝั่ง BackOffice Oracle) การพูดมั่นใจเกินหลักฐานทำให้ผู้ใช้ตัดสินใจเชื่อเร็วเกินไปได้
2. **KM/schema documentation ที่ลงทุนทำไว้ล่วงหน้าจ่ายผลตอบแทนทันทีตอนมี incident จริง** — การขุด schema แบบละเอียดครั้งเดียวช่วยให้ตอบคำถาม support แบบ ad-hoc ได้เร็วขึ้นมากในเซสชันถัดไป คุ้มค่าลงทุนแม้จะดูเหมือนงาน "เผื่ออนาคต" ตอนทำ
3. **เมื่อ user ส่ง query กลับมาขอปรับแค่จุดเดียว ให้แก้เฉพาะจุดนั้นและชี้ risk ที่ซ่อนอยู่ (เช่น operator precedence) แทนการเขียนใหม่ทั้งหมด** — เคารพสิ่งที่ user เขียนเองไว้แล้ว ไม่ over-write โดยไม่จำเป็น
