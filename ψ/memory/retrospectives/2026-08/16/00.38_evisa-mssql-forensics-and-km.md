## Honest Feedback

1. **macOS awk (one-true-awk) มี escape quirk ที่ไม่คาดคิด** — เวลาใช้ `-v pat="...\\[...\\]..."` เพื่อสร้าง dynamic regex ตัว backslash ที่ตั้งใจ escape ถูก awk กลืนหายไปเงียบๆ (ไม่ error แต่ pattern ผิด) ต้องเปลี่ยนไปใช้ `grep -F` + line-number + `sed` แทนถึงจะเสถียร เสียเวลา debug ไปหลายรอบ กับปัญหาที่ไม่ใช่ business logic เลย
2. **ไฟล์ CSV ใหญ่ (216MB/101MB/98MB) อยู่บน disk ที่ I/O ช้า** — grep/awk ธรรมดาที่ควรจบใน "วินาที" กลับใช้เวลาเกือบ 2 นาทีต่อไฟล์ ทำให้ต้อง `run_in_background` ซ้ำหลายรอบและรอ notification บ่อย กินเวลาการทำงานจริงไปพอสมควร (ไม่ใช่ปัญหาฝั่ง logic แต่เป็นข้อจำกัดสภาพแวดล้อม)
3. **ข้อความจากมอสสั้นมากตลอด session** (เช่น "query อะไรบ้าง", "booking ต้องมีอะไรบ้าง") — ต้องอนุมานเจตนาจาก context ทันทีทุกครั้งโดยไม่มีเวลาถามกลับ ส่วนใหญ่เดาถูกเพราะ context ต่อเนื่องชัดเจน แต่เป็นความเสี่ยงตีความผิดที่สะสมได้ถ้า session ยาวขึ้นเรื่อยๆ

## Lessons Learned

1. **อย่าใช้ตัวคั่น field (เช่น tab) ที่ payload อาจมีอยู่แล้ว** — เวลา parse/merge ข้อมูลที่เนื้อหาไม่รู้จักล่วงหน้า (เช่น SQL text จริงจาก production) ให้แยก field ด้วย `index()`/`substr()` แทนการตั้ง `FS`/`-F` ตรงๆ แล้ว **verify ผลลัพธ์ด้วยการ grep หา needle ที่รู้คำตอบอยู่แล้ว** ก่อนเชื่อว่า merge ถูกต้อง — อย่าเชื่อแค่ row count ตรงกัน
2. **ก่อนส่งข้อมูลให้ AI agent ภายนอก (เช่น zcode/agy ที่เรียก API ภายนอก) ต้องเช็คความอ่อนไหวของข้อมูลก่อนเสมอ** — โดยเฉพาะข้อมูล production ของระบบราชการ/regulated system ถามยืนยัน scope ก่อน แล้วกรองเหลือเฉพาะที่จำเป็นจริงๆ ก่อนส่งออกนอกเครื่องเสมอ
3. **สำหรับ legacy database ที่ไม่มีเอกสาร การขุด plan cache โดยเรียง execution_count คือเทคนิคที่ได้ผลสูง** — เผยให้เห็นว่า table/proc ไหนถูกใช้จริง (ไม่ใช่แค่มีอยู่) และมักเจอ trigger/business rule ที่ไม่มีเอกสารไหนพูดถึงเลย เหมาะเป็นขั้นแรกก่อนขอ full schema export เสมอเวลาต้องรับช่วงระบบที่ไม่มีใครส่งมอบงานให้
