## Lessons Learned

1. **When a report field name doesn't match any known column, check whether it's actually two
   separate resolved-name columns from the same master table joined via two different foreign
   keys on the same row** — before assuming it needs a new/unknown master table entirely. Here,
   "Country/Territories of Passport/TD" turned out to be `VDC_MST_COUNTRY.COUNTENM` joined via
   `PASSPORT_HOLDER_CODE`, sitting right next to `NATIONENM` (joined via `NATIONALITY_CODE`) in the
   exact same table — the two requested fields were never actually different tables, just different
   columns of one master table reached via two different FKs.
2. **A pre-built reporting view's row count matching the sum of a subset of raw-table status codes
   is strong, cheap evidence that the view silently excludes the other codes** — no need to inspect
   the view's SQL definition to prove this; `SUM(view total) ≈ SUM(raw codes A+C+R)` with `raw
   codes N+I` unaccounted for is enough to conclude the view scopes to terminal states only, and any
   non-terminal-state question must go to the raw table instead.
3. **Before combining two independently-sourced WHERE filters (e.g. a Visa Type literal from one
   turn and a Category literal from another), re-verify the *pair* together with a `GROUP BY`, not
   just each value individually** — both zero-row bugs caught this session were combinations of two
   filters that were each individually correct and confirmed in isolation, but had never been
   checked together. Individually-verified literals are not the same guarantee as a
   verified-together combination.
