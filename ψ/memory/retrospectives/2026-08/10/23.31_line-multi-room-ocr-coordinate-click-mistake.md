## Lessons Learned

- **When an interaction technique is powerful enough that Claude Code's own classifier gates it (e.g. raw coordinate clicks vs. AX-scoped actions), treat the block as a standing risk signal, not a one-time permission checkpoint.** Getting explicit user approval once doesn't retire the underlying risk — build the same precondition check (frontmost app verification, in this case) into *every* subsequent use of that technique for the rest of the session, not just the first one.
- **A dry-run/detection test is not the same as a smoke test of the actual mutating action.** `DRY_RUN=1` proved the chat list could be *found*; it said nothing about whether *clicking into it* actually worked. Before running a multi-step automation loop live, test the single riskiest primitive action (here: does clicking actually open a different room?) in isolation first, even if that costs one extra small interaction.
- **Blind coordinate-based UI automation on a machine with multiple visible windows must re-verify the target app is frontmost immediately before every single action, not once at the start of a sequence.** Focus can and does shift between a human's reply and the next automated step — especially in an async/background-job context where the human may switch windows while composing their message.
- **Custom-rendered desktop UI (Qt/Electron/canvas-based apps like LINE for Mac) can fail Accessibility on *both* the read side (empty content in the AX tree, found previously) and the write/interaction side (synthetic AXPress not registering, found this session) — these are separate failure modes and confirming one doesn't imply anything about the other. Test both explicitly before designing automation around either.**
