## Lessons Learned

- When evaluating whether to adopt an external framework/library into an existing production system,
  frame the real question as "does migrating solve a problem we actually have" rather than "is this
  framework good" — a mature, well-documented external project can still be a bad fit if the existing
  system already solves the actual operational problem (live state, deployment, notifications) that the
  external project doesn't even attempt to solve.
- GPL-3.0 (and copyleft licenses generally) only trigger on *distribution*, not private/internal use —
  before treating a GPL dependency as an automatic hard blocker, check whether the actual use case
  involves distributing the combined work to anyone. That said, defaulting to clean-room reimplementation
  anyway costs little when a translation between paradigms (e.g. Backtrader OOP → pandas vectorized) was
  already required for unrelated reasons, and it preserves optionality if distribution plans change later.
- A tuning result that improves multiple metrics *simultaneously* (not a tradeoff) is worth extra
  scrutiny before trusting, not less — the natural assumption is that risk and reward trade off, so a
  free improvement on both axes is either a real edge or a sign the sweep undersampled the parameter
  space; verify with the exact final config before writing it into production code, not just the
  multiplier that produced the promising sweep result.
- For any project that represents real ongoing work (deployed to production, iterated over multiple
  sessions), verify it's actually under version control early and explicitly — don't infer "this is
  safely tracked" from the fact that a repo exists at the parent level; a subdirectory can sit untracked
  for a long time with no error or warning surfacing that fact.
