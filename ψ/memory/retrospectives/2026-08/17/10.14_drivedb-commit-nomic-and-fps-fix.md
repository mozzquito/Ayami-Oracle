## Lessons Learned

- When a user reports a vague symptom that could map to multiple distinct root causes (e.g., "choppy audio" could mean live-monitoring glitches from an OS-level device change, or an actual defect baked into a recorded file), ask which scenario before investigating — the two paths can require completely different diagnostic tools and neither should be assumed from context alone, even when context makes one option feel more likely.
- For audio/video sync or stutter complaints, check the *declared* stream metadata (r_frame_rate, sample rate) against the *actual* measured values (frame count ÷ duration, packet timestamp deltas) before assuming the raw samples themselves are corrupted — a metadata/reality mismatch can produce audible playback artifacts even when the underlying data is intact, and this is a fast, cheap, falsifiable check to run before reaching for encoder-tuning changes.
- Two ffmpeg flags that look similar (an input-side rate hint like `-framerate 30` vs an output-side rate-normalization flag like `-r 30` placed after the input) can have opposite effects on a real-time capture pipeline — track which side of the ffmpeg command line a flag applies to, since input-side hints constrain what the capture device is asked to deliver while output-side flags reshape frames already captured, and conflating the two can lead to reapplying a previously-rejected fix under a different name.
- When a system-level change requires a reboot or GUI-only configuration step that can't be scripted (macOS driver installs, Audio MIDI Setup device routing), state the exact remaining steps clearly and stop — don't attempt partial automation or guess at whether the step succeeded; verify explicitly (e.g., `system_profiler` for the active output device) once the user confirms they've done it, rather than assuming based on elapsed time.
- The `/rrr` dig-miner's `ls -t "$PROJECT_BASE"/*.jsonl | head -1` pattern picks the most-recently-modified session file, not necessarily the current one — with multiple concurrent Claude Code sessions active in the same project directory, another session's activity can outrace the current one and get picked instead. This has now recurred at least twice (2026-08-15 and 2026-08-17). Always sanity-check dig-miner's returned snippets actually match the current conversation before merging them into a retro's Timeline; if they don't, re-derive the correct session ID from context (it's usually already been established earlier in the same conversation) and query that file directly instead.
