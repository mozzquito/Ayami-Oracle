## Honest Feedback

Three friction points specific to this session: (1) `/zcode` failed with an unhelpful generic "Turn execution failed" error twice in this session with no way to diagnose further — each failure just meant discarding that half of the second-opinion pair and moving on with agy's output alone, which works but means the "consult both" convention silently degrades to "consult whichever one didn't crash" without any visible signal to the user unless I call it out myself. (3) This session's multi-day, multi-topic shape (Discord digest → Kiro research → routine build → IT report → grafana-bot → log analysis → PDF summary) meant the retrospective itself had to reconstruct a lot of dropped context — the focus file being overwritten by unrelated work between sittings meant there was no reliable "what was I doing" breadcrumb to lean on other than the raw conversation transcript.

## Lessons Learned

- When probing an unfamiliar create/mutate API for its schema, assume every call is a live-effect action unless a documented dry-run/validate mode is confirmed first — a 200 response is not proof that the fields you sent were ignored, and "just testing" against a real account's endpoint can create real, persistent, connected objects.
- When a task depends on two independently-controlled prerequisites (e.g. a third-party app's repo access AND a separate environment's network policy), verify both end-to-end yourself before re-running, rather than proceeding on a single "ทำแล้ว" (done) confirmation for one of them — a shared failure mode (like a blocked network egress) will resurface identically until every dependency is independently confirmed, not just the one that was asked about.
- When delegating the same task to two sibling CLI agents for cross-checking, expect one to fail transiently sometimes — treat a single successful response as sufficient to proceed rather than blocking on both, but say so explicitly to the user rather than silently presenting only the survivor as if nothing else was tried.
