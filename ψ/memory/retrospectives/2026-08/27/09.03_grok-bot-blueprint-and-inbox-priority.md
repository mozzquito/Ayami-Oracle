### Key Code Changes

The inbox priority tag is a pure filename-convention change, not a schema migration:
`${PRIO:+${PRIO}_}` in the write-mode `FILE=` line expands to `P0_`/`P1_`/`P2_` when set
or nothing when untagged — chosen over an `if/else` branch for brevity, at the cost of
being non-obvious to a future LLM reading the skill (flagged by zcode, mitigated with an
inline comment, see below).

### Architecture Decisions

1. **Adapted `/learn`'s 3-agent codebase pattern to a non-code doc pack** rather than reading the ~58KB of markdown directly myself. In hindsight this was defensible but not clearly the cheaper choice — the pack was small enough that a direct read may have cost less context than 3 subagent round-trips plus their JSONL overhead. No regret strong enough to call it wrong, but not a clear win either.
2. **Inserted the priority tag as an optional filename segment rather than a new metadata file or frontmatter field** — cheapest possible change (zero schema migration, ~10 lines of skill-doc edit), matching zcode's explicit "biggest payoff for least effort" framing. Confirmed no other skill (`triage`, `talk-to`, `contacts`, `xray`, `team-agents`) parses `ψ/inbox/` filenames positionally, so the new segment was safe to insert.

   reachable; when one has a standing environment bug, the rule doesn't say when to stop

   in how the consult rule degrades, not just an agy bug.
2. **A month-long gap between doing the work and writing it up is a real process failure**,
   not just an artifact of how this transcript happens to be reviewed now. The work was

   review."
3. **Treating trailing command arguments (`/agy /zcode`) as an implicit standing
   instruction was a judgment call made silently.** It happened to be right here, but
   nothing in the transcript shows the alternative (asking) was even considered — for a
   session that reshaped the whole task around that reading, a one-line confirmation would
   have been cheap insurance.
