## Lessons Learned

1. When reusing a destination/convention from an existing agent or skill definition in the same
   repo, verify its git-tracking assumptions empirically (check `.gitignore` directly) before
   encoding move/write logic around it — a documented pillar table can drift from actual repo
   state, and copying another skill's convention doesn't inherit its correctness guarantees.
2. A synthetic sandbox test suite should mirror the target repo's actual `.gitignore` rules (and
   actual git-tracking state of the paths in question), not a clean/simplified stand-in — an
   ignore-interaction bug won't surface in a sandbox that never replicated the ignore pattern.
3. Before declaring a new mechanical script "done," run at least one live dry-run/smoke-test
   against real data in the target repo, even for a single low-stakes item — it can catch bugs
   that neither a second-opinion design review nor synthetic sandbox testing surfaces, because
   both of those only test what you thought to test.
