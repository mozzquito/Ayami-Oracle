## Lessons Learned

1. **When two systems model "the same" business process, don't assume shared concepts exist on
   both sides — verify structurally first.** MSSQL (front-end) and Oracle (BackOffice) share table
   naming conventions for master data but not for process-state concepts; "approve status" turned
   out to only exist on one side. A column-existence check (`INFORMATION_SCHEMA.COLUMNS` /
   `ALL_TAB_COLUMNS`) before writing the condition would have surfaced this immediately instead of
   after guessing candidate columns.

2. **Without a DB client, make every proposed query pull double duty as a schema probe.** When you
   can't connect to a database yourself, write queries that surface facts (an error message, a
   `SELECT DISTINCT`, a `INFORMATION_SCHEMA` lookup) as a side effect of the user running them —
   this turns an otherwise purely sequential propose→run→paste loop into one that also builds up
   verified schema knowledge for the next query.

3. **Never reuse an ID confirmed on one database instance for a different instance of "the same"
   schema, even under an identical name, without re-verifying.** Cross-DB master-data ID sync
   (confirmed once before for `PURPOSE_OF_VISIT_ID`) is the exception, not the default — the DTV
   `VISA_TYPE_ID=10` confirmed on Oracle was deliberately *not* reused on the MSSQL query; joining
   by name instead was the safer default until MSSQL's own ID gets confirmed separately.
