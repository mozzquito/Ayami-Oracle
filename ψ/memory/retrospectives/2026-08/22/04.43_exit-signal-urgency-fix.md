## Lessons Learned

- When classifying which events in a notification system are "urgent" vs "informational," check
  the classification against the actual downstream consequence of a human missing it, not against
  which side of the system (paper simulation vs. real execution) the event technically belongs to
  — a paper-trading system whose whole purpose is informing real trades has no truly "informational
  only" events if a human might be holding a matching real position.
- When infrastructure access is intentionally restricted (an SSH key deliberately not registered,
  a service intentionally not exposed), don't spend effort working around the restriction via
  increasingly indirect methods (`railway run` → discovering internal-hostname limits → reaching
  for `railway ssh`) — recognize the boundary quickly and switch to asking the human for the
  specific evidence needed instead. The workaround-hunting instinct costs time the direct ask
  doesn't.
- A second-opinion consultation (zcode/agy or otherwise) is scoped by the question asked, not by
  the full problem space — "analyze why X is slow" will not surface "does Y even happen at all,"
  even when Y is a sibling case of the same underlying issue. When investigating a class of
  problem (e.g., "notifications aren't reaching me in time"), explicitly enumerate every event
  type in scope rather than trusting that solving the most obvious instance covers the rest.
