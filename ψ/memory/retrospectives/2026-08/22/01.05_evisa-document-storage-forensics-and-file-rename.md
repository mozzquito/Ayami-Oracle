## Lessons Learned

1. **When a database's file-storage metadata is redundant across multiple columns (extension
   appearing in both a name field and a path field), any correction must update every redundant
   copy and the actual physical resource together, in a safe order** — verify the physical
   resource first, then update all DB columns atomically, then verify again before committing.
   Updating one column in isolation risks a state where the DB and the real file disagree.
2. **Before repeating a just-established fix pattern on a new record, check that record's current
   state first rather than assuming the same defect exists.** A fix that was necessary for one row
   (mismatched extension) is not automatically necessary for a superficially similar one — this
   session's second candidate record turned out to already have the correct extension in the data
   already visible from earlier in the conversation.
3. **On a production write action, propose the concrete replacement value as a question to
   confirm, not just as the finished statement** — even a well-reasoned inferred value (matching
   an established naming pattern) is still an assumption on the agent's part, and the level of
   caution applied to *which* value to write should match the caution already being applied to
   *whether* to write at all.
