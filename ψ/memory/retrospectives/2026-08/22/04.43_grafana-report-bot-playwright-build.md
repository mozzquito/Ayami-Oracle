## Honest Feedback

Three friction points specific to this session:

1. **The Bun/Playwright incompatibility cost a full debug cycle that shouldn't have been necessary.** `bun run src/cli.ts` is the natural dev-loop command in this repo's conventions, and it silently threw a cryptic internal error (`"/login" cannot be parsed as a URL"`) deep in `playwright-core`'s cookie-parsing internals — nothing about the error pointed at "wrong runtime." Diagnosing it meant trying the same code under plain Node before the real cause was obvious.

2. **VPN state is invisible until something times out.** The connectivity check to `10.0.163.250` silently hung for the full timeout window before failing — no fast-fail signal that the network had changed, which cost a round-trip of "let me check" → timeout → "please reconnect VPN" → recheck, entirely outside my control but still real session drag.

3. **The blank-panel bug had a genuinely confusing error signature.** `runRequest.catchError {cancelled: true}` sandwiched between two unrelated WebSocket-handshake-failure log lines doesn't read as "add a reload" on first glance — it took writing an isolated repro script with console-log capture to actually see the causal shape, rather than something inferable from the screenshot alone.

## Lessons Learned

1. **When a JS/TS tool works under `node` but fails under `bun run` (or vice versa) with an error deep inside a third-party library's internals, suspect the runtime shim before the library.** Playwright's cookie-parsing broke specifically on Bun's `node:http` polyfill, not on any code this session wrote — confirmed by running the identical unmodified code under both runtimes. This generalizes: cross-runtime compatibility issues in Node-ecosystem libraries often surface as confusing internal stack traces rather than an obvious "wrong runtime" message.

2. **A tool's own frontend accepting relative time strings ("now-7d") does not mean its underlying API does.** Grafana's dashboard URLs resolve `now-7d` client-side; the raw Prometheus HTTP API one layer underneath requires actual RFC3339/Unix timestamps. When building against a system with both a UI layer and a raw API layer, verify which layer actually performs time-string parsing rather than assuming the convenience syntax propagates all the way down.

3. **When a feature has no explicitly agreed threshold/rule, render it as neutral/informational rather than inventing one to make the output "look complete."** Applies beyond monitoring dashboards — any time a deliverable has an obvious slot for "is this good or bad" but the actual boundary was never specified, leaving it visibly unjudged is more honest than guessing a plausible-sounding cutoff.
