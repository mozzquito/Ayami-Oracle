## Honest Feedback

Three friction points specific to this session:

1. **Didn't warn before restarting a live MCP-hosting process.** As covered above — this is the clearest single miss. A one-line heads-up ("this will drop the current MCP session and AutoClaw's own internal connector sessions too, both need reconnect after") would have turned two later confused turns (stale session error, then the error-screenshot investigation) into zero.
2. **The "what can Ayami actually do with AutoClaw" boundary got explained three separate times** (OAuth login, "ask AutoClaw" chat, design/chat tools) instead of once, comprehensively, the first time it came up. Each individual answer was fine, but the user had to keep probing for the same underlying limit from different angles.
3. **No authoritative local source for the "credit" complaint.** There's no usage/billing file on disk — the real number lives on Z.ai's account dashboard. I inferred a plausible cause (`hermes-evolution` at 100%) from config and log-event counts, which was honest about being inference rather than a hard number, but I only mentioned "check the actual dashboard" as option 3 of 3 rather than leading with it as the most reliable path.

## Lessons Learned

1. **Before restarting or killing a process that hosts a live HTTP MCP endpoint, state upfront that every session connected to it (including the app's own internal self-connections) will drop and need reconnecting.** This is knowable in advance from how session-based MCP transports work — don't wait for the symptom (a tool error, or a confusing "error" status the user has to screenshot) to explain it after the fact.
2. **A consumer AI-agent app's "data connector" page (OAuth-based, e.g. Gmail/Drive) and its "MCP Servers" page (internal tool wiring) are two separate integration surfaces with no assumed overlap.** Verify what's externally reachable via MCP vs. purely internal to the app's own agent loop before investigating or promising either — conflating them wastes a full round-trip.
3. **State browser/desktop-automation boundaries (e.g. "I can only drive Chrome tabs, not arbitrary native/Electron apps, and won't enter credentials/OAuth on your behalf") once, clearly, the first time a UI-driving request for a non-Chrome app comes up** — not as three separate reactive explanations across the session.
4. **When investigating a third-party app's "cost/credit" complaint, check for local usage/billing telemetry first, then background-loop config toggles (heartbeat, self-evolution, cron) as corroborating evidence — and lead the answer with "check the vendor's own usage dashboard for the real number," not bury it as a caveat after the inferred cause.**
