## Lessons Learned

1. **Data that looks internally consistent (a value always paired with the same set of other
   values) is not the same as data that matches the intended business design.** Before asserting
   "this isn't a bug, it's consistent," ask whether an authoritative rule exists (spec, domain
   expert) that the pattern should be checked against — consistency is evidence of *causation*,
   not evidence of *correctness*. This is the second instance of this exact failure mode in one
   day (see also `2026-08-20_dont-theorize-bugs-from-unverified-blurry-ocr.md` for the sibling
   case, floating an unverified theory instead of asking first).
2. **A harness-provided identifier (like a scratchpad path embedding the real session ID) is a
   more reliable source of "what session am I actually in" than any mtime-based heuristic
   (`ls -t`), and should be checked FIRST, not as a fallback.** This session's dig-miner picked
   the wrong file via `ls -t` on at least two separate `/rrr` invocations across two days, while
   the correct ID was sitting in the system prompt's scratchpad path the entire time, unused.
   Any skill that needs "the current session ID" should extract it from that path rather than
   re-deriving it via file listing.
3. **When a fix for one error (e.g., dynamic SQL to route around Always Encrypted) triggers the
   exact same error it was meant to avoid, don't re-explain the original problem — say plainly
   that the fix didn't work and you don't have a confirmed reason why, then fall back to the
   simplest proven-working approach.** Guessing a plausible-sounding cause for an unexplained
   failure (as I did here, framing it as "probably a driver behavior") risks being taken as
   diagnosed fact rather than the speculation it actually is.
