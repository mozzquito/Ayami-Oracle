   most likely the Megvii box itself holding the only available concurrent

## Lessons Learned

1. **When the same device-side test is repeated multiple times with the
   same negative result, re-check the *live* configuration for parameters
   that affect test *timing or duration* before repeating the test
   identically again** — a threshold or zone setting is the obvious first
   thing to verify, but a duration/dwell-time requirement is easy to
   overlook and can invalidate every quick test run against it, even when
   every other config value is correct.
2. **A port reported "filtered" (not "closed" or "refused") by a port
   scanner, on a device that's known to be actively streaming to another
   consumer, is more likely a concurrent-connection limit than a firewall
   rule** — worth checking for an alternate/parallel access path (e.g., a
   web UI snapshot endpoint) before assuming the service itself is down.
3. **When a user's ambiguous short phrase ("this machine", "it", a bare
   pronoun) follows several turns of concentrated single-topic work, the
   default reading is almost always "the thing we've been talking about,"
   not a competing candidate introduced only implicitly** — a full-stop
   clarifying question is likely to read as unnecessary friction in that
   context; answering for the likely referent plus a one-line "did you
   mean X instead?" aside preserves both speed and correctability.
