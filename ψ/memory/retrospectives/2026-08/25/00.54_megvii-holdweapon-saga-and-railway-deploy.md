## Honest Feedback

1. **The `configure_alarm_push` double-protocol regression cost a full debugging cycle that could have been a five-minute check.** I added an `http://` prefix to `server_path` based on the web UI's input-box *placeholder text* ("http(https)://main(ip):port"), directly contradicting the literal XHR body I had already captured and documented in the same function's own docstring minutes earlier (`"server_path":"192.168.1.4:8788"`, no prefix). The bug produced total silence (no error anywhere — the device just never connected) rather than a loud failure, so it took re-opening the browser and visually spotting `http://http://...` in the rendered form field to catch it.

2. **Long real-world gaps (hours, sometimes overnight) between messages made state assumptions stale repeatedly** — the alarm-bridge process died at least twice from being killed during idle periods, the Mac's own LAN IP changed via DHCP multiple times requiring re-`configure-push`, and the device's own alarm backlog replayed non-monotonic old timestamps that looked like a live flood before I realized it was a retry queue draining. None of these were wrong calls exactly, just the genuine cost of debugging a physical device across a day with real-world interruptions rather than a tight continuous session.

3. **`nmap -sn` segfaulting on the full `/24` sweep (exit 139) while single-host scans worked fine** was a new, unexplained tool failure this session hadn't seen before — worked around with a plain parallel `ping` loop, but never root-caused why nmap itself crashed rather than just failing permission-wise like the earlier TCC issue from the prior retro.

## Lessons Learned

1. **When a device's own web UI accepts a form value the API docs don't literally match (e.g. an input box's placeholder implying a format the underlying stored field doesn't actually use), trust the intercepted XHR body over the visual UI hint** — a form field can *display* a value with cosmetic prefixing/formatting for the user's convenience while storing something structurally different underneath.
2. **Any relay/bridge that spawns a subprocess or opens a new external-service connection per event must have a concurrency cap and per-type cooldown from the very first version, not added reactively** — especially for any pipeline sitting downstream of a device/API whose true event volume hasn't been fully characterized yet. The cost of over-defending early is near zero; the cost of an unbounded spawn loop discovered via `ps aux` after the fact is real (rate limits, resource exhaustion, silent noise burying the actual signal).
3. **Before declaring an ML/AI detection feature "not working," check whether the vendor documents an explicit maturity/readiness tier** (here: "L4, implementation stage, lab-conditions-only") — this reframes "config is wrong" investigations into "this needs conditions I may not be able to provide" investigations, which changes both the debugging strategy and when to stop.
4. **A relay meant to run 24/7 for physical-device event delivery should default to being deployable as a standalone public service (webhook/HTTPS calls), not built assuming co-location with sibling scripts in a local monorepo checkout** — the "local machine must stay on" constraint is often not stated as a requirement up front but turns out to matter a lot once asked about directly.
