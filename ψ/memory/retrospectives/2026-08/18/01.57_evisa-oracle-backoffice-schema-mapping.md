## Lessons Learned

1. **When a report/UI field looks like a raw code but exported data shows resolved text, check
   for a pre-built reporting VIEW before manually joining master tables.** This eVisa system (and
   likely similar enterprise systems) ships `VW_*` views that already resolve every FK to its
   display name — `VW_GET_APPLICATION_CCDC` replaced a 6-table manual join entirely. Search
   `ALL_TAB_COLUMNS`/`INFORMATION_SCHEMA.COLUMNS` for the exact field names from the target output
   (not just the obvious ID columns) before assuming a hand-built join is necessary.
2. **Timestamp string format is a fast, reliable RDBMS fingerprint for an unknown data export.**
   Oracle `TIMESTAMP WITH TIME ZONE` renders as `DD-MON-YY HH.MI.SS.FFFFFFFFF AM/PM REGION/CITY`
   (dot-separated, named IANA region); MSSQL `datetimeoffset` renders as
   `YYYY-MM-DD HH:MM:SS.fffffff ±HH:MM` (colon-separated, numeric offset). Worth checking before
   assuming which schema doc applies to a mystery export.
3. **The same status/enum concept can have two different vocabularies in the same system** — raw
   table columns vs. derived reporting views. Always run a `GROUP BY <status_col>` to see actual
   distinct values before hardcoding a filter literal; a value confirmed correct in one table is
   not guaranteed to be the same literal in a related view.
4. **A view name that reads as a scoped verb-phrase (e.g. `VW_SENT_...`) is a signal to check
   before using it as ground truth for a status that might logically precede or exclude that
   step** — check row counts or business logic implications first, not after a 0-row surprise.
