## Lessons Learned

- Shell aliases defined in `.zshrc` (or similar interactive-shell-only config) do not resolve inside a `run_in_background: true` Bash call, even when the exact same command string works fine in a foreground Bash call in the same session — background execution appears to skip whatever interactive-shell sourcing foreground calls get. When a tool is invoked via an alias (check with `type <name>` or `alias` if uncertain), prefer resolving and using its underlying real command/path for anything that might run in the background, rather than relying on the alias resolving.
- When independently verifying one specific claim by running a real command, stay alert to *any* error the command produces, not just whether it confirms or denies the specific claim being checked — an unrelated failure surfacing during a targeted verification step can be a sign of real environment drift (dependency/runtime version mismatches, stale native builds) that has nothing to do with the thing being investigated, and is easy to miss if you're narrowly focused on one hypothesis.
- When a user reports a symptom you cannot reproduce after a genuine, real attempt, say so plainly and ask for more specific detail (exact wording, a screenshot, the precise trigger) rather than guessing at a plausible-sounding fix — an unverified guess risks either wasting effort fixing the wrong thing or, worse, being presented with false confidence as "the fix" when the actual cause is still unknown.
- For any migration on a NoSQL-adjacent structure that doesn't support in-place schema changes (like FTS5 virtual tables, which can't `ALTER TABLE ADD COLUMN`), wrap the drop/recreate/backfill sequence in a single database transaction so a mid-migration failure rolls back cleanly instead of leaving the database in a half-migrated state with data loss risk.
