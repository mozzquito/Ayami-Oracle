## Lessons Learned

- **When proposing to read a personal messaging/social app's UI on macOS, check both Accessibility and Screen Recording permission state up front, in the same ask** — the two TCC gates feel like one thing ("let this app see the screen") to a non-technical user but macOS treats window-structure introspection and pixel capture as entirely separate grants. Bundling the ask avoids a second surprise permission trip after the user has already committed to a path based on an incomplete cost description.
- **Before building automation around a native app's Accessibility tree, verify a single leaf node's raw `properties of` output rather than trusting a flattened `entire contents` dump** — custom-rendered UI (Electron/Qt/canvas-based chat apps, confirmed here with LINE for Mac) can show structural roles (window/list/row) in a tree dump while every leaf's `description`/`value`/`name` is genuinely empty. A flattened dump can look encouraging; only a direct `properties of` query on the actual leaf confirms whether real content is exposed.
- **A Dock icon's `AXStatusLabel` attribute (queried via `System Events → process "Dock"`) exposes an app's unread-badge count even when that app's main window is otherwise inaccessible** — useful as a low-effort, reliable fallback signal ("is there new activity") for any app whose deeper UI resists Accessibility scraping.
- **Official APIs for consumer messaging/social platforms (LINE Messaging API, Facebook Graph API) are scoped to business/bot use, not personal-account monitoring** — LINE's API only powers Official Accounts that others message directly; Facebook's Graph API has had no viable personal-feed/group-read path for third-party or self-built apps since 2018. When a request implies "read my own personal inbox/feed via API," say so plainly and pivot to on-device alternatives (Accessibility, OCR, browser automation with the user's own session) instead of chasing an API scope that doesn't exist for that use case.
