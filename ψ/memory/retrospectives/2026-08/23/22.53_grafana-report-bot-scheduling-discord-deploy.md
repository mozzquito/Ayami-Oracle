## Lessons Learned

1. **อย่าเชื่อ log 15 วินาทีแรกของ background job ที่คาดว่าใช้เวลาหลักนาที — ต้องรอจนจบหรือเช็ค exit status จริงก่อนรายงานว่า "สำเร็จ"** โดยเฉพาะงานที่ trigger ผ่าน scheduler จริง (launchd/cron) ซึ่งอาจมี failure mode ที่ direct-run ไม่เจอ (เช่น sleep/PATH/permission ต่างจาก interactive shell).

2. **เมื่อ deploy ระบบอัตโนมัติที่พึ่งพา VPN/network ภายนอก ให้ถือว่า "reachable ตอนเช็ค" ไม่เท่ากับ "reachable ตลอดการทำงาน"** — VPN ที่ flaky อาจผ่าน pre-flight check แต่หลุดกลางทาง ควรมี retry logic ตั้งแต่เริ่มออกแบบถ้ามีสัญญาณว่า network ไม่เสถียร ไม่ต้องรอให้ fail จริงก่อนค่อยเพิ่ม.

3. **ในโปรเจกต์ TypeScript ที่ใช้ ES modules + dotenv: อย่าอ่าน `process.env.X` เป็น module-level constant ในไฟล์ที่ถูก import โดยไฟล์ entrypoint ที่เรียก `dotenv.config()`** — static import ทั้งหมดถูก hoist ไปทำงานก่อนโค้ดในไฟล์ entrypoint เสมอ ไม่ว่าจะเขียน `import` ไว้บรรทัดไหนก็ตาม ถ้าต้องการค่า env ที่โหลดจาก `.env` ให้อ่านแบบ lazy (ในฟังก์ชัน ไม่ใช่ top-level) เสมอในไฟล์ที่ไม่ใช่ entrypoint เอง.

4. **เมื่อ sibling-agent (zcode/agy) consult ล้มเหลวด้วย environment/permission reason ซ้ำมากกว่า 2 ครั้งในวันเดียว ให้หยุดพยายามทันที ไม่ต้องลอง workaround ต่อ** — บันทึกไว้ใน memory เพื่อ session ถัดไปจะได้ไม่เสียเวลาซ้ำ (ทำไปแล้วรอบนี้กับ agy).
