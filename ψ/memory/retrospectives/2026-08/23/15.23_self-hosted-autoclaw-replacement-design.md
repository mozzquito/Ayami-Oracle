## Session Summary

Mos opened with an ambiguous question — "can Ayami create a claw and connect it, and make a cronjob?" I initially answered it as if it meant AutoClaw (a closed-source desktop AI agent app investigated heavily in yesterday's sessions), explaining AutoClaw's connector states (all disconnected) and Claude Code's own session-only `CronCreate` tool. Mos corrected me: not AutoClaw — could Ayami herself create an "openclaw" or "hermes"? I searched the repo's own retrospectives/learnings from the prior day and found both terms were actually AutoClaw's own internal naming (`~/.openclaw-autoclaw/openclaw.json` config format, and a `hermes-evolution` self-improvement skill inside it that was burning credits) — not external projects. A clarifying AskUserQuestion round resolved the real ask: build a self-hosted system Ayami fully owns, replacing just the two things actually needed from AutoClaw (Gmail/Calendar/Drive OAuth access + persistent cron), given AutoClaw's own security concerns (exec-without-confirmation, a live plaintext bearer token found in its config, the credit-draining self-evolution loop) documented in prior sessions.

Followed the SDLC-gate requirement stage: batched scope questions into one AskUserQuestion round (all 3 connectors together; OAuth-credential source and code-location/cron-mechanism deferred to design stage, per mos's choice). Drafted an initial design (dedicated GCP OAuth client, custom local OAuth callback server, macOS Keychain token storage, custom stdio MCP server via `@modelcontextprotocol/sdk`, launchd for cron, code under `ψ/lab/`) and consulted both zcode and agy per the standing CLAUDE.md rule to get a second opinion before validating a design. Both flagged real, overlapping problems: Keychain access from a `launchd` agent can hit a locked/no-GUI-session failure; a GCP OAuth client left in "Testing" mode caps refresh tokens at a 7-day TTL; `launchd` needs absolute paths and explicit environment variables since it doesn't source shell profiles; and an MCP stdio server is meant to be launched on-demand by a client, not run as a persistent daemon (cron and MCP should be separate programs sharing a library, not one thing).

zcode also claimed several existing open-source Gmail/Calendar/Drive MCP servers existed (one link it flagged itself as "no, wrong one" mid-answer) — rather than trust that outright, I ran an independent WebSearch + WebFetch pass and found something zcode/agy didn't know about: Google itself now hosts official remote MCP servers for Gmail, Calendar, and Drive (`gmailmcp.googleapis.com` etc.), and Claude Code's own CLI already supports registering exactly this kind of OAuth-gated remote HTTP MCP server (`claude mcp add --transport http ... --client-id ... --client-secret -s user`, `claude mcp login`). This collapses the whole design — no custom OAuth server, no custom MCP server code, no token storage/refresh logic to write at all, since Claude Code manages OAuth credentials internally once registered. The only remaining pieces are: a dedicated GCP project + OAuth consent screen (human-only steps mos would need to click through), registering the three official MCP endpoints at user scope, and a `launchd` plist invoking `claude -p "<prompt>"` on a schedule for persistent cron (replacing the session-only `CronCreate` tool). Presented this simplified design back to mos and asked what the first cron job should actually *do* — session ended there, awaiting an answer, before mos invoked `/rrr` the next day.

## Lessons Learned

1. **Before invoking a sibling CLI agent (zcode/agy) in a mode that hit a documented failure before, check `ψ/memory/learnings/` for that agent's known quirks first** — the fix should be applied proactively on the first attempt, not rediscovered by hitting the same already-documented bug again.
2. **When a delegated second-opinion agent (zcode, agy, or any sibling CLI) names specific external tools, libraries, or repos as reasons to simplify a design, verify those claims independently (WebSearch/WebFetch) before trusting them** — especially when the agent itself flags uncertainty (e.g. "no, wrong one" mid-answer). In this session that verification step is what surfaced the actually-correct, more authoritative answer neither sibling agent had.
3. **A new/unfamiliar term in the user's first message that partially overlaps with heavy recent context deserves a clarifying question before being answered** — don't let a strongly-loaded prior session bias the interpretation of a genuinely ambiguous new term.
4. **When a second opinion's punch list converges on the same root problem from two independent agents (here: Keychain + launchd's no-GUI-session conflict, and the GCP OAuth "Testing" mode 7-day trap), treat that convergence as high-confidence signal to redesign around it**, not just a caveat to note and proceed past.
