## Honest Feedback

Three friction points specific to this session:

1. **AskUserQuestion misuse for open-ended questions.** I tried to use the tool for the wizard's batch freetext phase (name/purpose/likes) and it hard-errored because it requires ≥2 concrete options — it's not built for open-ended collection. Wasted a call before falling back to plain text output, which is what the skill actually specifies.

2. **Permission layers didn't compose the way I expected.** The user answered "yes, push it" via AskUserQuestion, but the underlying `git remote set-url` + `git push` still hit the auto-mode classifier and got blocked separately, requiring an explicit re-ask ("approve and get permission now"). Two confirmation systems, no shared state between them, and I didn't flag that gap until it happened.

3. **Lost track of commit state across an interruption.** The `[Request interrupted by user]` landed at almost the exact moment I was one tool call away from `git commit`. Everything after that (issue redirect, remote repoint, push) proceeded on the unverified assumption that the commit existed. This is the kind of gap that's easy to create and easy to miss — I should treat any interruption near a write operation as a signal to re-verify state before continuing, not just resume the plan.

## Lessons Learned

- Before stating a git operation is "done" in any user-facing summary, run `git log`/`git status` to confirm — don't reconstruct state from intent, especially across a conversation interruption boundary.
- `AskUserQuestion` requires 2–4 concrete, mutually exclusive options; it cannot collect open-ended freetext. For wizard-style "tell me about yourself" phases, present the questions as plain text and wait for the reply instead.
- A user's "yes" inside `AskUserQuestion` does not automatically satisfy the auto-mode permission classifier for the underlying tool call it authorizes — expect consequential git/network actions (remote changes, pushes) to need a separate, explicit approval even after the user has already agreed in principle.
- When inheriting a repo cloned from a template, grep for the previous owner's home-directory paths (`/Users/<name>/...`) across both executable files (hooks/scripts) *and* config (`.gitignore`, `settings.json`) — a single bad `.gitignore` line can silently blackhole an entire directory from version control with no error.
