## Lessons Learned

- **When delegating security-relevant code changes to any agent — including yourself, mid-edit — write and run concrete test cases against the actual before/after behavior before trusting a "fixed" claim.** A confident, well-organized explanation of what was fixed is not evidence that it works; only running it is.
- **`set -e` exempts a failing command inside a `command && VAR=assignment` list, but does NOT exempt a failing pipeline inside a plain `VAR=$(pipeline)` substitution** — the two look similar but have different `set -e` interaction rules in bash. When writing new shell code under `set -e`, test the exact failure path (e.g. "what happens when the grep finds nothing") rather than reasoning about it in the abstract.
- **BSD tools and GNU tools on the same macOS system can support different regex extensions for the same flag** — this system's `/usr/bin/grep -E` accepts `\s` as whitespace, but `/usr/bin/sed` does not, even though both claim POSIX ERE-adjacent support. Don't assume a regex feature that works in one text tool works in a sibling tool on the same box; verify each one.
- **When a user pastes a suspiciously complete, pre-formed technical answer that references context you don't have (a "part 2" of something, a command that doesn't match anything in the actual environment), check whether it's copy-pasted from a real external source before either blindly executing it or dismissing it as fabricated** — in this case `find`-ing for plausible filenames in Downloads turned up the real source material in under a minute.
- **When ingesting a human's personal data export (social media, etc.) into any persistent memory, scope explicitly with them first, and default to excluding anything a third party wouldn't have consented to (partner names, phone numbers, family members) even when the human doesn't ask you to** — narrow scope by default, widen only on request, not the other way around.
