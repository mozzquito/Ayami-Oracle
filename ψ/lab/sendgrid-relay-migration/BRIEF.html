SendGrid Relay Brief

ย้าย SMTP relay ขาออกจาก Exchange on-prem ไป Twilio SendGrid โดย MX และ mailbox ยังอยู่ที่ Exchange ตามเดิม สรุปนี้แยกสิ่งที่ยืนยันแล้ว สิ่งที่ยังไม่รู้ และสิ่งที่ยังไม่ควรสัญญา

ปริมาณเป้าหมาย
200,000 ฉบับ/วัน
เฉลี่ยรายชั่วโมง
≈ 8,300 ฉบับ/ชม.
เทียบรายเดือน
≈ 6 ล้าน ฉบับ/เดือน
ระยะเวลารวม (ประมาณการ)
6–9 สัปดาห์

เส้นทางเมลหลังย้าย

แอปไม่ต้องแก้ ทีม server เปลี่ยนที่ Send Connector ของ Exchange จุดเดียว (ข้อเสนอ D2 แบบ 1 ยังรอมอสยืนยัน)

  1. แอป > 3 ระบบเช่น Thai eVisa และผู้ใช้ Outlook ทุกคน
  2. Exchange on-premSend Connector ตัวใหม่ (ทีม server)
  3. SendGridsmtp.sendgrid.net:587 STARTTLS, user apikey
  4. เซิร์ฟเวอร์รับของผู้รับหาเจอผ่าน MX เช่น Gmail, Outlook.com, โดเมนราชการ
  5. กล่องเมลผู้ใช้ปลายทางที่ผู้รับอ่านเมล

DNS ไม่ใช่จุดที่เมลวิ่งผ่าน เป็นตัวช่วยข้างทาง 3 อย่าง: (1) Exchange และ SendGrid หา IP ของกันและหา MX ของผู้รับ (2) เซิร์ฟเวอร์ผู้รับใช้ SPF, DKIM, DMARC ที่เราเพิ่มใน DNS ตรวจว่าเมลไม่ปลอม (3) bounce ไปที่ return-path ของ SendGrid ผ่าน CNAME

เมลขาเข้าไม่เปลี่ยน: อินเทอร์เน็ต → MX → Exchange → mailbox. SendGrid ไม่มี mailbox จึงใช้เป็นทางส่งออกอย่างเดียว

ข้อมูลที่มอสแจ้ง

ทั้งหมดมาจากมอส ยังไม่ใช่คำยืนยันจากลูกค้า

หัวข้อสถานะรายละเอียด
ขอบเขตระบุแล้วทุกเมลขาออกย้ายไป SendGrid (D1 = A) ปริมาณรวมทั้งหมดต้องไม่เกิน 200k/วัน รวมเมลผู้ใช้ด้วย
ระบบที่ส่งเมลระบุแล้วมากกว่า 3 ระบบ ทีม frontend/backend ดูแลฝั่งแอป และอีกทีมดูแลฝั่ง server
แอปที่อ่าน NDR/bounceไม่มีปิดความเสี่ยง R1 แต่ผู้ใช้ Outlook ยังอาจคาดหวัง NDR (R12)
ปริมาณจริงไม่ทราบมอสระบุว่าไม่สนใจ แต่ปริมาณจริงกำหนดขนาดแผนและตาราง warm-up (R13)
เวอร์ชัน Exchangeไม่ทราบไม่ขวางแผน แต่ทีม server ต้องรู้ตอนทดสอบคำสั่ง
DNSไม่ชัดผู้ให้บริการและผู้ดูแลยังไม่ชัด ต้องถามซ้ำ ถ้าอยู่บน Cloudflare ต้องตั้ง CNAME เป็น DNS-only
เครือข่ายยังไม่ทราบต้องทดสอบพอร์ต 587 ไปที่ smtp.sendgrid.net ก่อน
Logต้องแก้แผนมอสจะใช้ SendGrid API แต่เก็บย้อนหลังได้ราว 30 วัน ไม่พอสำหรับ TOR ≥ 90 วัน

สามเรื่องที่ควรรู้ก่อนเข้าห้อง

จุดที่คำตอบเดิมยังไม่พอ

Log ผ่าน API ไม่พอสำหรับ ≥ 90 วัน

API ที่ดึง log ค้นได้เฉพาะช่วงที่ SendGrid เก็บเอง (สูงสุดราว 30 วันแม้แผนจ่ายเงิน) ถ้า TOR ต้องการ 90 วันขึ้นไป ต้องรับ Event Webhook แล้วเก็บลง DB ของเราเอง POC อยู่ที่ ψ/lab/sendgrid-log-poc/ แต่ทดสอบระดับ 50–100 ฉบับ ยังไม่เคยทดสอบที่ 200k/วัน

ปริมาณจริงที่ไม่ทราบมีผลต่อแผน

200k เป็นตัวเลขเป้าหมาย ไม่ใช่ปริมาณที่วัดได้ ทีม server ดึงจาก Exchange message tracking 30 วันได้เอง โดยไม่ต้องรอลูกค้า ถ้าไม่ดึง ต้องยอมรับความเสี่ยงชนเพดานแล้วเมลค้าง

ผู้ใช้ Outlook อาจไม่ได้รับ NDR ยังไม่ verify

เมื่อรวมเมลผู้ใช้ตาม D1 = A ถ้าพิมพ์ที่อยู่ผิด Exchange ปัจจุบันส่ง NDR กลับถึงกล่องผู้ใช้ แต่ SendGrid ตามที่จำได้จะรับเมลแล้วบันทึก bounce เป็น event ควรแจ้งลูกค้าล่วงหน้าและยืนยันพฤติกรรมกับ SendGrid

การตัดสินใจที่ยังค้าง

รหัสคำถามสถานะ
D1ย้ายเมลขาออกทั้งหมดหรือเฉพาะแอปA ทั้งหมด
D2เส้นทาง: (1) แอป → Exchange → SendGrid หรือ (2) แอปต่อ SendGrid ตรงแนะนำ (1) รอยืนยัน
D3ค่อยๆ เพิ่มปริมาณตามโดเมนผู้รับ หรือตามแอป (เมื่อใช้ (1) ทำแบบโดเมนผู้รับผ่าน address space ได้)เปิด
D4แผน SendGrid ที่รับ 200k/วัน และจำนวน Dedicated IP (ต้องคุย sales)เปิด
D5แยก subuser ตามระบบหรือไม่เปิด

สิ่งที่ต้องขอจากลูกค้า

  • ผู้ให้บริการ DNS และผู้ดูแลต้องเพิ่ม CNAME ของ Domain Authentication และรวม SPF (SPF มีได้ record เดียวต่อ domain)
  • รายชื่อแอปทั้งหมดและเจ้าของแต่ละระบบรวมค่า From address และ domain ที่ใช้ส่ง
  • เวอร์ชัน Exchange, ผู้มีสิทธิ์แก้ Send Connector, change window และ lab สำหรับซ้อม
  • ผลทดสอบพอร์ต 587 จากเครือข่ายจริง
  • ข้อกำหนดข้อมูลส่วนบุคคลและความลับราชการเมลจะวิ่งผ่านระบบ SendGrid ในต่างประเทศ ยังไม่ได้พิจารณาเรื่อง PDPA ในเอกสารใดเลย
  • ข้อกำหนด log retention จริง และผู้รับผิดชอบเก็บ log
  • ใครเป็นผู้ config จริง และเราเข้าไปช่วยหรือดูผ่านหน้าจอได้ไหมถ้าลูกค้าทำเอง ต้องส่งมอบคู่มือ (ยังไม่ได้เขียน HANDOVER-KIT)

บอกลูกค้า และยังไม่ควรสัญญา

บอกให้ชัดตั้งแต่ต้น

  • SendGrid ไม่ใช่ mailbox hosting ใช้ส่งออกอย่างเดียว
  • ต้องมี Dedicated IP และ warm-up จึงไม่ใช่สลับทีเดียวในวันเดียว
  • พฤติกรรมเปลี่ยน: bounce ไปที่ SendGrid, มี suppression list, ต้องปิด click/open tracking สำหรับเมลระบบ
  • ต้องมี DNS change และรอ propagation
  • ระยะเวลา 6–9 สัปดาห์ เป็นประมาณการ ไม่ใช่คำสัญญา

ยังไม่ควรสัญญา ยังไม่ verify

  • แผนที่รับ 200k/วัน และ ≥ 10,000/ชม. (คาดว่าเกินแผนมาตรฐาน ต้องได้ยืนยันเป็นลายลักษณ์อักษร)
  • ตาราง warm-up และจำนวน Dedicated IP
  • คำสั่ง Exchange ใน runbook ยังไม่เคยรันจริง และยังไม่ยืนยันว่าเวอร์ชันของลูกค้าทำได้ตามที่เขียน
  • อัตราส่งถึง inbox ตอน POC Gmail ทิ้งเมลเงียบๆ และอีกโดเมนเข้า Junk
  • ราคา ยังไม่มีข้อมูล

ความเสี่ยงหลัก

รหัสความเสี่ยงมาตรการ
R13ไม่ทราบปริมาณจริง เลือกแผนและ warm-up ไม่ถูกดึงจาก Exchange message tracking ก่อนตกลงแผน
R12ผู้ใช้ไม่ได้รับ NDR เมื่อพิมพ์ที่อยู่ผิดแจ้งผู้ใช้ก่อนย้าย ยืนยันพฤติกรรมกับ SendGrid
R14เมลถึงโดเมนของเราเอง อาจวนออกไป SendGrid แล้ววนกลับ MX ของ Exchange ยังไม่ verifyตั้งให้โดเมนตัวเองส่งภายในเสมอ ไม่ให้ address space ของ Send Connector ครอบโดเมนตัวเอง และทดสอบใน lab ก่อน
R5ปริมาณกระโดดโดยไม่ warm-up ถูก throttle หรือเข้า spamทำตามตารางที่ SendGrid ยืนยัน ห้ามข้ามขั้น

R9เมลหายเงียบที่ปลายทางทดสอบหลายผู้ให้บริการ ดูกล่อง inbox จริง ไม่ดูแค่สถานะ delivered
R4SPF ซ้ำหรือเกิน 10 lookupsรวมกับ record เดิม นับ lookup
R3Click/Open tracking เขียนลิงก์ในเมลระบบใหม่ปิดตั้งแต่ Phase 1
